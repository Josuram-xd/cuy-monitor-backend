# Guía de despliegue del backend (avance del 30 de septiembre)

> **Meta:** que en AWS queden corriendo y conectados **PostgreSQL 18, Kafka 4.3, el backend Spring Boot 4.1 (Java 25) y Caddy con HTTPS**, y poder demostrarlo con 3 URLs. Sin lógica de negocio todavía; eso viene después.
>
> Junto con esta guía va el archivo **`backend-deploy-kit.zip`**, que trae todos los archivos listos para copiar al repo (Dockerfile, docker-compose, Caddyfile, `application.yml`, la migración V1 y 3 clases Java mínimas).

---

## Qué vas a tener al final

```
Internet ──HTTPS──► Caddy (:443) ──► backend (Spring Boot :8080) ──► PostgreSQL 18
                     cuymonitor.duckdns.org          │
                                                      └──► Kafka 4.3 (KRaft)
                                                            events.camera / events.audio
                                                            events.weight / alerts.cage
```

Todo corre en **una EC2** con Docker Compose. Kafka y Postgres **no** se exponen a internet; solo Caddy tiene puertos abiertos.

Las 3 pruebas de que funciona:

| URL | Qué prueba | Respuesta esperada |
|---|---|---|
| `GET https://<dominio>/actuator/health` | El backend está vivo y ve la base de datos | `{"status":"UP"}` |
| `GET https://<dominio>/api/system/status` | Flyway creó las tablas en Postgres | `{"cages":1, ...}` |
| `POST https://<dominio>/api/system/ping` (con `X-API-Key`) | El backend publica en Kafka y se consume a sí mismo | `{"sent":"<uuid>", ...}` + una línea `Received event` en los logs |

## Parte 1: en tu computador (≈ 1 hora)

### 1.1 Instalar lo necesario

| Herramienta | Versión | Para qué |
|---|---|---|
| JDK | **Temurin 25** ([adoptium.net](https://adoptium.net)) | Compilar y correr el backend |
| Docker Desktop | la última | Postgres y Kafka en local |
| Git | cualquiera reciente | — |
| IDE | IntelliJ IDEA o VS Code con Extension Pack for Java | — |

No hace falta instalar Maven: el proyecto trae su propio wrapper (`mvnw`).

### 1.2 Generar el proyecto en Spring Initializr

Entra a [start.spring.io](https://start.spring.io) y pon:

| Campo | Valor |
|---|---|
| Project | **Maven** |
| Language | Java |
| Spring Boot | **4.1.x** (la más alta que NO diga SNAPSHOT ni M/RC) |
| Group | `com.cuymonitor` |
| Artifact | `backend` |
| Package name | `com.cuymonitor.backend` |
| Packaging | Jar |
| Configuration | **YAML** (si no aparece la opción, borras `application.properties` después) |
| Java | **25** |

**Dependencias** (botón *ADD DEPENDENCIES*):

- Spring Web *(en Boot 4 el artefacto se llama `spring-boot-starter-webmvc`)*
- Spring Data JPA
- PostgreSQL Driver
- Flyway Migration
- Validation
- WebSocket
- Spring for Apache Kafka
- Spring Boot Actuator
- Lombok
- Testcontainers

*GENERATE* → se descarga `backend.zip`.

### 1.3 Meterlo en el repo

```bash
git clone https://github.com/<tu-usuario>/cuy-monitor-backend.git
cd cuy-monitor-backend
# Descomprime backend.zip y copia su CONTENIDO (no la carpeta) aquí
# Luego descomprime backend-deploy-kit.zip y copia el contenido de
# cuy-monitor-backend/ encima (acepta reemplazar application.yml si pregunta)
```

Si Initializr generó `src/main/resources/application.properties`, **bórralo** (usamos `application.yml`).

Revisa en el `pom.xml` que estén `spring-boot-starter-webmvc`, `spring-boot-starter-flyway` y `flyway-database-postgresql`. Si falta la última, agrégala dentro de `<dependencies>`:

```xml
<dependency>
    <groupId>org.flywaydb</groupId>
    <artifactId>flyway-database-postgresql</artifactId>
</dependency>
```

(Sin versión: la maneja Spring Boot.)

Lo que queda del kit dentro del repo:

```
cuy-monitor-backend/
├── Dockerfile
├── .dockerignore
├── .gitattributes                  ← important if you use Windows (see 1.6)
├── infra/
│   ├── docker-compose.yml          ← production (EC2)
│   ├── docker-compose.dev.yml      ← local: Postgres + Kafka only
│   ├── Caddyfile
│   ├── .env.example
│   └── .gitignore                  ← keeps .env out of git
└── src/main/
    ├── resources/
    │   ├── application.yml
    │   └── db/migration/V1__initial_schema.sql
    └── java/com/cuymonitor/backend/
        ├── BackendApplication.java           ← generated by Initializr
        ├── config/KafkaTopicsConfig.java     ← creates the 4 topics on startup
        ├── ingestion/kafka/EventConsumer.java← logs every event it receives
        └── api/SystemController.java         ← /api/system/status and /api/system/ping
```

**Qué hace cada clase (resumen):**

- `KafkaTopicsConfig`: declara los 4 tópicos; Spring los crea solos al arrancar si no existen. Por eso ya no hace falta el script `create-topics.sh`.
- `EventConsumer`: escucha `events.camera`, `events.audio` y `events.weight` y solo escribe en el log. Es la clase que tu compañero después convierte en la entrada del Factory Method.
- `SystemController`: dos endpoints de prueba. `status` cuenta las jaulas en Postgres y `ping` publica un mensaje en Kafka (pide la API key). Cuando el sistema real funcione, se puede borrar.

### 1.4 Levantar Postgres y Kafka en local

```bash
docker compose -f infra/docker-compose.dev.yml up -d
docker compose -f infra/docker-compose.dev.yml ps      # both should be "running"
```

### 1.5 Correr el backend en local

```bash
./mvnw spring-boot:run          # Windows: mvnw.cmd spring-boot:run
```

En el log tienes que ver, en este orden:
1. `Successfully applied 1 migration` (Flyway creó las tablas)
2. `Tomcat started on port 8080`
3. Nada de `Connection to localhost:9092 could not be established` repitiéndose (eso significaría que Kafka no está)

Pruebas:

```bash
curl http://localhost:8080/actuator/health
curl http://localhost:8080/api/system/status
curl -X POST http://localhost:8080/api/system/ping -H "X-API-Key: dev-key"
```

Después del `ping`, en la consola del backend debe aparecer:

```
Received event topic=events.camera key=cage-1 value={"ping":"..."}
```

Si ves esa línea, **Postgres, Kafka y el backend están conectados**. Eso mismo es lo que vas a repetir en AWS.

### 1.6 Probar la imagen Docker (opcional pero recomendado)

```bash
docker build -t cuy-monitor-backend:local .
```

Si falla con `./mvnw: not found` o `/bin/sh^M: bad interpreter`, es por los saltos de línea de Windows. El `.gitattributes` del kit lo evita para los próximos clones; para arreglar tu copia actual:

```bash
git add --renormalize .
git commit -m "chore: normalize line endings"
```

### 1.7 Subir al repo

```bash
git checkout -b feature/deployment-setup
git add .
git commit -m "feat: initial Spring Boot 4.1 setup with Kafka, Postgres, Flyway and Docker deployment"
git push -u origin feature/deployment-setup
```

Abre el Pull Request, que tu compañero lo revise y hagan merge a `main`.

**Revisa antes de hacer commit** que `infra/.env` NO esté en `git status` (solo `.env.example`).

## Parte 2: preparar AWS (≈ 30 min)

### 2.1 Seguridad y control de gastos (hazlo primero)

1. Entra a la consola de AWS con la cuenta nueva.
2. **MFA en la cuenta root:** menú de tu nombre → *Security credentials* → *Assign MFA device* (con Google Authenticator o similar).
3. **Usuarios para los dos:** IAM → *Users* → *Create user*, uno para cada uno, con la política `AdministratorAccess` y acceso a la consola. Desde ahí trabajan con esos usuarios, no con root.
4. **Alerta de gasto:** *Billing and Cost Management* → *Budgets* → *Create budget* → plantilla *Monthly cost budget* de **$10**, con tu correo. También revisa *Credits* para ver cuánto crédito te queda.
5. Arriba a la derecha elige la región **US East (N. Virginia) `us-east-1`**: es la más barata y la latencia desde Colombia es buena. Todo lo que sigue se crea en esa región.

### 2.2 ¿Qué tamaño de máquina? (corrección importante al plan)

En la versión anterior del plan puse t3.medium y dije que su costo era una fracción pequeña de los créditos. **Eso estaba mal calculado.** Con los precios de `us-east-1` (aproximados, bajo demanda, 24/7):

| Tipo | RAM | ¿Elegible en plan gratuito? | Costo aprox./mes | 2 meses (oct–nov) |
|---|---|---|---|---|
| **t3.small** | 2 GB | Sí | ~$15 | ~$30 |
| t3.medium | 4 GB | **No** | ~$30 | ~$60 |
| c7i-flex.large | 4 GB | Sí | ~$62 | ~$124 |
| m7i-flex.large | 8 GB | Sí | ~$70 | ~$140 |

Con créditos de $100 (que pueden llegar a $200), la decisión es:

- **Ahora (avance, sin IA):** **t3.small + 4 GB de swap.** Backend + Kafka + Postgres + Caddy caben en ~1.2 GB si limitamos la memoria de Java (ya viene así en el `docker-compose.yml`).
- **Cuando entre el ai-service (fin de octubre):** se detiene la instancia, se cambia el tipo a **c7i-flex.large** y se vuelve a encender. Dura 2 minutos y no se pierde nada.
- En las cuentas nuevas con plan gratuito, AWS solo deja lanzar los tipos elegibles (t3.micro, t3.small, t4g.micro, t4g.small, c7i-flex.large, m7i-flex.large). Por eso t3.medium ya no es opción.

Además hay dos costos pequeños: la IP pública (~$3.6/mes) y el disco de 30 GB (~$2.4/mes).

### 2.3 Crear la instancia EC2

EC2 → *Launch instance*:

| Campo | Valor |
|---|---|
| Name | `cuy-monitor-server` |
| AMI | **Ubuntu Server 26.04 LTS**, arquitectura **64-bit (x86)** |
| Instance type | **t3.small** |
| Key pair | *Create new key pair* → nombre `cuy-monitor-key`, tipo **ED25519**, formato `.pem`. **Guárdalo bien**; sin él no entras al servidor |
| Network settings → *Edit* | *Create security group* llamado `cuy-monitor-sg` con 3 reglas: **SSH (22) → My IP**; **HTTP (80) → Anywhere 0.0.0.0/0**; **HTTPS (443) → Anywhere 0.0.0.0/0** |
| Storage | **30 GiB gp3** |

*Launch instance*.

**Kafka (9092) y Postgres (5432) NO se abren.** Nunca.

Pásale el `.pem` a tu compañero por un canal privado (no por el repo). Y si tu IP de casa cambia, tienes que actualizar la regla de SSH (EC2 → Security Groups → `cuy-monitor-sg` → *Edit inbound rules* → *My IP*).

### 2.4 IP fija (Elastic IP)

EC2 → *Elastic IPs* → *Allocate Elastic IP address* → *Allocate*. Luego *Actions* → *Associate Elastic IP address* → elige `cuy-monitor-server` → *Associate*.

Anota esa IP; la vamos a llamar `ELASTIC_IP`.

### 2.5 Dominio gratis con DuckDNS

1. Entra a [duckdns.org](https://www.duckdns.org) e inicia sesión con GitHub.
2. Crea un subdominio, por ejemplo `cuymonitor` → queda `cuymonitor.duckdns.org`.
3. En el campo *current ip* pon la `ELASTIC_IP` y dale *update ip*.
4. Comprueba desde tu computador (puede tardar unos minutos):

```bash
nslookup cuymonitor.duckdns.org      # must return your ELASTIC_IP
```

Caddy necesita que el dominio apunte a la IP **antes** de arrancar; si no, no puede sacar el certificado HTTPS.

## Parte 3: preparar el servidor (≈ 20 min)

### 3.1 Entrar por SSH

```bash
# Linux / macOS / Git Bash
chmod 400 cuy-monitor-key.pem
ssh -i cuy-monitor-key.pem ubuntu@ELASTIC_IP
```

En Windows con PowerShell también funciona `ssh -i .\cuy-monitor-key.pem ubuntu@ELASTIC_IP`. Si se queja de los permisos del archivo, clic derecho → Propiedades → Seguridad → deja solo a tu usuario.

### 3.2 Actualizar y crear swap de 4 GB

```bash
sudo apt update && sudo apt -y upgrade

sudo fallocate -l 4G /swapfile
sudo chmod 600 /swapfile
sudo mkswap /swapfile
sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab

free -h        # "Swap: 4.0Gi" must appear
```

El swap evita que la máquina se quede sin memoria mientras Maven compila la imagen.

### 3.3 Instalar Docker

```bash
sudo apt install -y docker.io docker-compose-v2 docker-buildx git
sudo systemctl enable --now docker
sudo usermod -aG docker ubuntu
exit
```

Vuelve a entrar con el mismo comando `ssh` (para que tome el grupo `docker`) y verifica:

```bash
docker version
docker compose version
```

(Uso los paquetes de Ubuntu porque vienen probados con 26.04. Si algún día necesitas la versión más nueva de Docker, está el script oficial `curl -fsSL https://get.docker.com | sh`.)

### 3.4 Clonar el repo

Si el repo es **público**:

```bash
mkdir -p ~/cuy-monitor && cd ~/cuy-monitor
git clone https://github.com/<tu-usuario>/cuy-monitor-backend.git
```

Si es **privado**, crea en GitHub un *fine-grained personal access token* (Settings → Developer settings → Personal access tokens → Fine-grained) con acceso **solo** a `cuy-monitor-backend` y `cuy-monitor-ai-service`, permiso *Contents: Read-only*, y vencimiento en diciembre. Luego:

```bash
mkdir -p ~/cuy-monitor && cd ~/cuy-monitor
git clone https://github.com/<tu-usuario>/cuy-monitor-backend.git
# Username: your GitHub username
# Password: paste the token (not your GitHub password)
git config --global credential.helper store    # so it doesn't ask again on git pull
```

Más adelante, cuando esté listo el ai-service, se clona al lado:

```
~/cuy-monitor/
├── cuy-monitor-backend/
└── cuy-monitor-ai-service/     ← later
```

### 3.5 Configurar los secretos

```bash
cd ~/cuy-monitor/cuy-monitor-backend/infra
cp .env.example .env
openssl rand -hex 24      # run it twice: one for POSTGRES_PASSWORD, one for API_KEY
nano .env
```

Deja el `.env` así (con tus valores):

```
DOMAIN=cuymonitor.duckdns.org
POSTGRES_DB=cuymonitor
POSTGRES_USER=cuymonitor
POSTGRES_PASSWORD=<first random value>
API_KEY=<second random value>
```

Guarda con `Ctrl+O`, `Enter`, `Ctrl+X`. Pásale la `API_KEY` a tu compañero por privado; la van a usar el edge_agent y el serial_bridge.

**Ojo:** si cambias `POSTGRES_PASSWORD` después de la primera vez que levantas Postgres, no toma efecto (la contraseña queda guardada en el volumen). Decídela bien desde el principio.

## Parte 4: levantar todo (≈ 10 min, la primera vez tarda más por la compilación)

```bash
cd ~/cuy-monitor/cuy-monitor-backend/infra
docker compose up -d --build
```

La primera vez descarga las imágenes y compila el backend con Maven; en una t3.small puede tardar **5–10 minutos**. Mira el avance:

```bash
docker compose ps
```

Espera a que se vea algo así:

```
NAME                   SERVICE    STATUS
cuy-monitor-postgres-1 postgres   Up (healthy)
cuy-monitor-kafka-1    kafka      Up (healthy)
cuy-monitor-backend-1  backend    Up
cuy-monitor-caddy-1    caddy      Up
```

Logs del backend (sal con `Ctrl+C`; los contenedores siguen corriendo):

```bash
docker compose logs -f backend
```

Busca `Successfully applied 1 migration` y `Tomcat started on port 8080`.

Logs de Caddy, para confirmar que sacó el certificado:

```bash
docker compose logs caddy | grep -i "certificate obtained"
```

## Parte 5: verificar (lo que muestras en el avance)

Desde **tu computador** (no desde el servidor):

```bash
# 1. Backend alive + database reachable
curl https://cuymonitor.duckdns.org/actuator/health
# → {"status":"UP"}

# 2. Flyway created the tables
curl https://cuymonitor.duckdns.org/api/system/status
# → {"service":"cuy-monitor-backend","cages":1,"time":"..."}

# 3. Kafka round trip
curl -X POST https://cuymonitor.duckdns.org/api/system/ping -H "X-API-Key: <your API_KEY>"
# → {"sent":"<uuid>","topic":"events.camera"}
```

Y en el servidor:

```bash
docker compose logs backend | grep "Received event"
# → Received event topic=events.camera key=cage-1 value={"ping":"<same uuid>"}
```

Comprobaciones extra, directo contra Kafka y Postgres:

```bash
# The 4 topics exist
docker compose exec kafka /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 --list

# Tables created by Flyway
docker compose exec postgres psql -U cuymonitor -d cuymonitor -c '\dt'
```

Y desde afuera, confirmar que Kafka y Postgres **no** son accesibles (tiene que fallar o quedarse esperando):

```bash
nc -zv -w 5 ELASTIC_IP 9092
nc -zv -w 5 ELASTIC_IP 5432
```

Con esto el avance queda cumplido: **backend desplegado en AWS, con Kafka en Docker, Postgres y HTTPS.**

## Parte 6: el día a día

### Desplegar una versión nueva

```bash
ssh -i cuy-monitor-key.pem ubuntu@ELASTIC_IP
cd ~/cuy-monitor/cuy-monitor-backend
git pull
cd infra
docker compose up -d --build backend
docker compose logs -f backend
```

Solo se recompila y reinicia el backend; Postgres y Kafka siguen con sus datos.

### Comandos útiles

| Para qué | Comando (desde `infra/`) |
|---|---|
| Ver el estado | `docker compose ps` |
| Ver logs de un servicio | `docker compose logs -f backend` (o `kafka`, `postgres`, `caddy`) |
| Reiniciar un servicio | `docker compose restart backend` |
| Apagar todo (sin borrar datos) | `docker compose down` |
| Encender todo | `docker compose up -d` |
| Consumo de memoria/CPU | `docker stats` |
| Memoria de la máquina | `free -h` |
| Entrar a Postgres | `docker compose exec postgres psql -U cuymonitor -d cuymonitor` |
| Leer un tópico desde el inicio | `docker compose exec kafka /opt/kafka/bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic events.camera --from-beginning` |
| **BORRAR** todo, incluida la base de datos | `docker compose down -v` ⚠️ |

### Si se reinicia la máquina

No hay que hacer nada: Docker arranca solo (`systemctl enable docker`) y los contenedores tienen `restart: unless-stopped`.

### Cuando llegue el ai-service

```bash
cd ~/cuy-monitor
git clone https://github.com/<usuario>/cuy-monitor-ai-service.git
cd cuy-monitor-backend/infra
docker compose --profile ai up -d --build
```

Antes de eso, cambia la instancia a **c7i-flex.large**: EC2 → selecciona la instancia → *Instance state* → *Stop* → *Actions* → *Instance settings* → *Change instance type* → `c7i-flex.large` → *Start*. La Elastic IP y los datos se mantienen.

## Parte 7: si algo falla

| Síntoma | Causa probable | Solución |
|---|---|---|
| `./mvnw: not found` o `bad interpreter` al construir | Saltos de línea de Windows en `mvnw` | Ver 1.6 (`.gitattributes` + `git add --renormalize .`) |
| Postgres se reinicia en bucle; el log habla de `PGDATA` y de `/var/lib/postgresql/18/docker` | El volumen está montado en `/var/lib/postgresql/data` (así era hasta Postgres 17) | Montarlo en `/var/lib/postgresql`, como viene en el kit |
| El backend repite `Connection to node -1 (localhost/127.0.0.1:9092) could not be established` | No está leyendo `KAFKA_BOOTSTRAP`, o Kafka no ha terminado de arrancar | Revisar que el `environment` del backend tenga `KAFKA_BOOTSTRAP: kafka:9092`; `docker compose ps` debe mostrar Kafka `healthy` |
| En local, el backend no conecta a Kafka pero en Docker sí (o al revés) | `ADVERTISED_LISTENERS` distinto en cada compose | Local usa `localhost:9092` (dev.yml); en el servidor, `kafka:9092`. No mezclar los archivos |
| `Schema-validation: missing table` al arrancar | Se creó una entidad JPA sin su migración | Crear `V2__...sql` con la tabla. **Nunca** editar `V1` después de haberla aplicado |
| Flyway avisa que PostgreSQL 18 es "newer than this version" | Solo es una advertencia | Se puede ignorar |
| Caddy no saca el certificado (`challenge failed`, `timeout`) | El dominio no apunta a la IP, o los puertos 80/443 están cerrados | `nslookup` del dominio; revisar el security group; luego `docker compose restart caddy` |
| `502 Bad Gateway` en `/api/...` | El backend todavía está arrancando o se cayó | `docker compose logs backend` |
| El servidor se pone lentísimo o un contenedor aparece con `Exited (137)` | Se quedó sin memoria | `free -h`, confirmar que el swap está activo; bajar `-Xmx`; si ya está el ai-service, subir a c7i-flex.large |
| `Permission denied (publickey)` al hacer SSH | Llave equivocada, usuario equivocado o cambió tu IP | Usuario `ubuntu`; `.pem` correcto; actualizar la regla SSH a *My IP* |
| `401 invalid API key` en `/ping` | El header no coincide con `API_KEY` del `.env` | Copiar la clave exacta, sin espacios |
